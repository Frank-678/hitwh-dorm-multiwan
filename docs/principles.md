# 原理与性能边界

## 为什么一个墙口能出现多个“设备”

RAX3000M 的物理 WAN 为 `eth1`。Linux `macvlan` 可以在该端口上创建多个具有独立 MAC 的虚拟设备，例如 `macwan2`、`macwan3`。每个虚拟设备独立发送 DHCP 请求，因此校园网交换侧会看到多个终端。

在已验证的 HITwh 寝室环境中，同一墙口允许多个 MAC 同时获得 `10.240.0.0/16` 地址，网关均为 `10.240.255.254`。每个 MAC 仍必须提前通过锐捷 ePortal 认证；获得 DHCP 地址不代表已经通过认证。

## 为什么需要独立路由表

多个 WAN 位于同一个 IPv4 子网并使用同一个网关。如果只依赖 Linux 主路由表，内核无法可靠区分应从哪个 MAC 发包。

项目为每条线路建立独立路由表：

| 接口 | 连接标记 | 路由表 |
|---|---:|---:|
| `wan` | `0x101` | 101 |
| `wan2` | `0x102` | 102 |
| `wan3` | `0x103` | 103 |
| `wanN` | `0x100 + N` | `100 + N` |

nftables 只在尚未标记的新 TCP/UDP 连接出现时选择标记。默认使用 `numgen inc mod N` 轮询在线出口，TCP、UDP 使用独立生成器；`balance_mode=random` 可恢复原有的 `numgen random mod N`。连接跟踪把标记保存在整个会话中，随后策略路由根据标记选择对应的路由表和出口。

在线集合和算法未变化时不重建 nftables 规则，轮询序列在健康检查之间继续运行。出口集合或算法变化时，在一个 nftables 事务中更新新连接选择规则，已建立连接仍沿用原标记。单出口时直接使用唯一标记。

轮询只改善新连接分配，不根据实时接收速率调整权重，也不迁移既有 NAT 连接。小流量连接和大下载连接仍可能分到同一出口；HTTP/2 的多个流可复用一个 TCP 连接。实测数据见 [分流算法验证](load-balancing.md)。

## 这是负载均衡，不是单连接绑定

一个 TCP 连接的两端只看到一个源地址，因此不能在三条出口之间随意切换。单线程下载仍受单个认证终端的限速影响。多个并行连接可以分散到不同出口，所以多线程下载器、BT、多个设备同时使用时才会接近总带宽之和。

真正让同一 TCP 连接跨线路叠加通常需要远端聚合服务器、MPTCP 或隧道两端配合，本项目不包含这些组件。

## 启动瞬时高速

校园网很可能采用令牌桶或类似突发限速。空闲时积累的突发额度允许下载开始时短暂超过稳定速率；额度耗尽后回落。长期允许的数据量近似满足：

```text
允许数据量 <= 稳定速率 × 时间 + 突发额度
```

不断重建连接通常不会提高长期平均速度，因为同一认证终端的连接共享限速器。项目通过多个合法认证终端获得多个独立的稳定速率，而不是利用瞬时突发。

## 健康检查

每条线路使用自己的 IPv4 源地址访问配置的 `204` 检查页（默认是 HTTP）：

- 返回预期 `204`：加入负载均衡池。
- 被重定向到 ePortal、响应码不符或超时：退出池。
- DHCP 恢复且健康检查通过：自动重新加入。

检查并行执行，因此线路增加时不会线性延长一次刷新所需时间。

健康检查与路由配置分开处理：未变化的路由和策略规则保持原样，可用出口集合变化时只更新新连接的选择规则。更新 nftables 时使用同一个事务，并核对实际规则，以便防火墙重载后恢复分流。

不能先删除所有策略规则、清空路由表，再逐路重建。中间空档可能让已标记连接回落到默认 WAN，MASQUERADE 发现出口设备变化后会删除连接跟踪，造成副出口下载周期性停滞。项目为已安装的策略表保留高 metric 的不可达默认路由：正常默认路由存在时优先使用正常线路；线路路由缺失时停止该连接的转发，避免换成另一个 NAT 出口。真实线路失效后，应用仍可能需要重建连接；普通 TCP 不能无缝迁移到另一个 NAT 地址。

## 路由器自身的主备切换

客户端连接由 `prerouting` 标记分流，路由器自身发起的普通连接则需要单独选择出口。`router_failover=1` 时，更新器优先选择健康的主 WAN；主 WAN 离线后优先保留仍健康的当前副出口，否则选择编号最小的健康副 WAN。主 WAN 恢复后自动切回。

优先级 `32000` 的策略规则查询主路由表，但忽略默认路由，以保留 LAN 和其他具体目的地的路由；`32001` 只匹配本机发起、低 12 位标记为零的流量，查询选中 WAN 的既有策略表。它们排在每条 WAN 的连接标记、源地址规则以及常见 Tailscale 规则之后，因此不会把健康检查或既有下载连接改到另一个 WAN。选择不变时不改规则；替换出口规则时先添加新规则，再删除旧规则。主路由表由 netifd 继续管理。

DNS 必须在第一次健康检查之前可用。安装器在首个 dnsmasq 实例没有自定义 `serversfile` 时接入 `/var/run/hitwh-mwan.dns`；更新器读取有地址线路的 DHCP DNS，包括 `peerdns=0` 时位于 `inactive` 的服务器，生成 `server=DNS地址@线路源地址`。源地址策略规则将查询导向对应 WAN，而不是依赖尚未选出的默认出口。DNS 列表变化时原位更新文件并发送 SIGHUP，不重启 WAN；列表不变时不发送信号。原位更新保留文件 inode，兼容 OpenWrt dnsmasq 的文件挂载。

`hitwh-mwan-dns` 在启动顺序 18 创建受管的空 DNS 文件，早于 dnsmasq 的顺序 19；这样重启后不会因 `/var/run` 被清空而让 dnsmasq 读取不存在的文件。顺序 95 的主监控服务随后填入 DHCP DNS 并通知 dnsmasq 重读。

所有健康检查失败时，在线数显示零，不把失败线路计为在线。若上次默认出口仍有地址，则暂时保留它并显示 `router_state=unverified`，避免检测站点故障时盲目改到另一条未经验证的线路；若没有可保留的出口，则移除这两条选择规则并显示 `unavailable`。这不保证该出口可用。关闭功能后移除选择规则和受管 DNS 项，恢复由主路由表决定本机默认出口。

## 上限

持续总速度受以下最小值限制：

1. 各认证终端限速之和；
2. 寝室墙口与路由器端口的 1 Gbit/s 物理速率；
3. 校园网对单墙口的聚合限制；
4. RAX3000M 的软件 NAT 与策略路由性能；
5. 下载服务器、Wi-Fi、网线和客户端存储性能。

默认 16 路是脚本的管理上限，不代表校园网或路由器一定能稳定承载 16 个认证终端。
